## مسئولیت‌ها و چرخهٔ عمر

| جزء | مسئولیت |
|---|---|
| Desktop / کاربر عادی | نمایش، انتخاب صریح، چهار زبان، DPAPI، اشتراک، وضعیت حساب و فرمان محدود |
| Agent / همان کاربر | مالک انحصاری سراسری هر SID، دریافت IPC با CurrentUserOnly، اجرای هسته، تنظیم و بازیابی پراکسی |
| Xray | HTTP/SOCKS روی loopback؛ یک outbound و بدون fallback مستقیم؛ TLS/REALITY با اعتبارسنجی اصلی |
| ProxyLease | ثبت durable پیش از تغییر؛ حفظ PAC/AutoDetect/bypass/flags؛ بازیابی فقط در صورت تعلق تنظیمات به همین نشست |
| Runtime / ProcessJob | کنترل فرایند و Job Object با KILL_ON_JOB_CLOSE؛ drain محدود بدون ثبت خروجی خام |
| TUN broker / آینده | دسترسی مدیریتی محدود، مالکیت route/DNS/TUN و ژورنال مستقل؛ در نمونهٔ فعلی وجود ندارد |

اتصال: اعتبارسنجی کانفیگ → تأیید هش هسته → Job → اجرای Xray → کانفیگ از stdin →
آمادگی listener محلی با مهلت ۱۰ثانیه → ثبت recovery و تنظیمات قبلی → اعمال پراکسی.
آمادگی listener تأیید HTTPS نیست؛ تست HTTPS جدا و اختیاری است. اتصال دستی به
پینگ، اسکن، فایل وضعیت حساب یا مقصد تست وابسته نیست. UDP در این نمونه فعال نیست.

قطع: بازیابی تنظیمات متعلق به نشست → بستن هسته و Job → بستن IPC و Agent.
EOF رابط، خروج والد، مرگ هسته یا تغییر آدرس شبکه، لغو و پاک‌سازی را آغاز می‌کند.
در صورت تغییر هم‌زمان تنظیمات توسط کاربر/اپ دیگر، تنظیمات جدید بازنویسی نمی‌شوند؛
ژورنال باقی می‌ماند و خطای تعارض مشخص نشان داده می‌شود.

مرگ رابط: Agent زنده پاک‌سازی می‌کند. مرگ Agent: Job هسته را می‌بندد و رابط زنده
recovery را اجرا می‌کند. اگر همهٔ فرایندها هم‌زمان terminate شوند یا برق قطع شود،
بازیابی فوری تضمین نمی‌شود؛ RunOnce همان کاربر در ورود بعدی و بازیابی در اجرای
بعدی برنامه برای این حالت ثبت شده‌اند. غیرفعال‌شدن RunOnce توسط سیاست Windows
نیازمند بازیابی دستی است. تمام این مسیرهای native هنوز روی Windows آزمایش نشده‌اند.

پراکسی سیستم فقط تنظیم WinINET پیش‌فرض همان کاربر/LAN را مدیریت می‌کند؛
WinHTTP، تمام برنامه‌ها، اتصال dial-up/VPN، UDP و DNS کل دستگاه را پوشش نمی‌دهد.
هیچ route یا DNS سیستم در نمونهٔ فعلی تغییر نمی‌کند. این نمونه kill switch نیست.

## حریم خصوصی و اعتماد

کانفیگ و URL اشتراک فقط در فایل DPAPI مربوط به همان کاربر نگه داشته می‌شوند؛
نسخهٔ قابل‌انتقال یا export حفاظت‌شده ساخته نمی‌شود. نام pipe و PID در آرگومان‌ها
هستند؛ اعتبارها نیستند. named pipe سرور یک کاربر دارد و پروفایل را دوباره می‌خواند.
هیچ primitive اجرای فرمان یا مسیر executable از رابط پذیرفته نمی‌شود.

DPAPI در برابر مدیر سیستم یا کد در حال اجرای همان حساب، ضمانت محرمانگی مطلق نیست.
TLS نامعتبر پذیرفته نمی‌شود؛ SSH هنوز فعال نیست و تا ساخت جریان تأیید هویت جدا
نباید فعال شود. گزارش تشخیصی فقط نسخه/سیستم/مرحله/زمان/کد خطای ثابت دارد.
هیچ ثبت مداوم آمار، اسکن دائمی یا حلقهٔ heartbeat در بیکاری وجود ندارد.


## گسترش preview.2

Agent یک Job برای Xray، میزبان Go و در صورت نیاز Naive دارد. هستهٔ داخلی DNS یک
listener خصوصی دارد و درگاه جلویی میزبان حداکثر ۶۴ client را می‌پذیرد. هیچ scan یا
probe شرط شروع نیست. helper از stdin یک JSON محدود می‌خواند و EOF همهٔ منابع را
می‌بندد؛ stdout فقط ready/error/trust ساخت‌یافته است. TLS و SSH هویت مستقل دارند.

کلید عمومی SSH در DPAPI همان پروفایل نگه داشته می‌شود. تغییر سرور یا کلید نیازمند
پذیرش مجدد اثر انگشت است. تأیید کاربر از راه UI مستقل از آزمون HTTPS انجام می‌شود.
Naive فقط نام فایل تصادفی را در argv می‌گیرد؛ فایل از لحظهٔ ایجاد ACL حفاظت‌شدهٔ
همان SID دارد، handle با DeleteOnClose تا قطع نگه داشته می‌شود. این جزئیات native
در WindowsSmoke اضافه شده‌اند ولی اجرای واقعی Windows همچنان باقی است.

آزمون مجموعه حداکثر یک Agent در هر لحظه دارد، هر بار بدون system proxy؛ سه نمونهٔ
پایداری، سنجش بلندمدت نیست. توقف pipe را می‌بندد و منتظر پاک‌سازی Agent می‌ماند.
ابزار DNS فقط پاسخ DNS را بررسی می‌کند و به‌عنوان تست تونل یا سرعت معرفی نمی‌شود.

## اسکن در preview.6

Desktop یک worker Go با ورودی/خروجی استاندارد، هش پین‌شده و Windows Job Object ایجاد می‌کند. دیتای پروفایل، credentials و URL در خط فرمان نمی‌آیند. Worker نتیجهٔ هر ترکیب IP/انتقال را مستقل گزارش می‌کند. درخواست E2E از Agent جدا با --probe-pipe استفاده می‌کند. این حالت نه mutex مالک شبکه را می‌گیرد، نه recovery را اجرا می‌کند، و تنظیم پراکسی سیستم در آن مجاز نیست. حداکثر دو آزمون کامل در یک اسکن هم‌زمان‌اند. کانال اصلی Agent همچنان تنها مالک پراکسی کاربر است.
