Veyra roadmap and desktop feasibility — 2026-11-04

Current alpha05 scope
- Real test uses the actual Android VPN/proxy service for each protocol, one profile at a time. It requests HTTPS through the explicit local SOCKS listener; direct fallback is prohibited.
- Three fresh verified HTTPS 204 responses from www.gstatic.com/generate_204. Median includes SOCKS connection, remote connection, TLS and response status. Setup time is separate; spread is max minus min; this is not ICMP RTT, throughput, UDP forwarding verification or long-term stability.
- Bulk test requires disconnected state; grant VPN permission once first (unless proxy-only mode). Temporary service connections are stopped between profiles. Current single-profile connection can be tested without stopping it. Stop cancels further samples and cleans up owned service.
- Default sort uses verified HTTPS latency. Optional short-test reliability sort uses success fraction then latency. TCP reachability is explicitly unverified and ranks after verified HTTPS. Results are session-local and time-stamped, not evergreen measurements.
- Import/create menus classify paths (Web/TCP, UDP, DNS/alternative), not measured speed. No protocol has a universally fastest or most stable rank. After import, use the test for this network. DNS paths are fallback candidates, not guaranteed to bypass filtering.
- Android service transitions, TUN routing and device UI are not validated in this environment. Automated tests cover SOCKS/TLS/HTTP behavior, ranking, parser and lifecycle on JVM/Linux.

Visual redesign (next implementation stage)
- Home: connection status, one main connection button, selected profile and best tested candidate.
- Profiles: search and path filters; show verified latency, success count, last-tested time and unknown state distinctly.
- Simple view by default; protocol details, raw configuration and diagnostics in advanced sections.
- Separate settings/help/support screens; Persian and English text, RTL layout and accessibility/font scaling.
- No automatic profile switching until connection lifecycle, DNS leak protection and retry policy are verified on devices.

Desktop feasibility
Evidence from current source: app/build.gradle.kts is Android-only (com.android.application, kotlin android, Hilt); service uses Android VpnService; native assets are Android ABI executables/JNI libraries. They cannot be packaged unchanged as Windows/macOS/Linux builds.
The repository also contains a Go CLI (cli/main.go, cli/direct.go, cli/Makefile) with SOCKS proxy operation and a Windows cross-build target. This is reusable starting material, not an already validated Veyra desktop application and not proof of full protocol parity.
Recommended architecture: shared Kotlin/JVM profile models, validation, ranking and Compose UI where portable; OS-specific service/routing/credential storage and packaging; pinned native cores run as supervised subprocesses. CoreForm and TunnelProbe are already largely JVM-portable. CoreLink still uses Android Base64 and needs an adapter. Hilt, Android navigation, Android clipboard and permission APIs need adapters or replacement.
Compose Multiplatform is the first candidate because the app is Kotlin/Compose. Tauri is a feasible alternative but requires rebuilding the UI in web technologies; do not migrate frameworks merely to change appearance.
Start desktop with the four Xray-backed protocols plus standard imports, and explicitly audit legacy DNS/SSH/Tor/Naive availability separately. Do not advertise Full parity until each engine is built and tested for each OS.
Windows: native core builds, background service or privileged helper for system-wide routing, DNS restoration, installer and signing, suspend/resume and network-change tests.
macOS: Intel/Apple Silicon build choice, privileged/network integration, signed nested cores, Developer ID signing/notarization for public distribution, system tests on a real Mac.
Linux: supported distro/architecture scope, privilege separation and TUN/routing integration, service lifecycle, package formats and network-manager interaction tests.
Suggested order: Android stability and design foundation; Windows prototype; Linux; macOS with access to a Mac and signing setup. No desktop installers were produced in this change.

Publication preparation
- Two repositories under the user's ownership: app/client and manager, with reproducible build instructions, original license notices, protocol support matrix and known limitations.
- GitHub Releases with APK, hashes, source tag, changelog and verified signing-certificate fingerprint; Issues templates for OS/version, network type, protocol and sanitized logs. SECURITY.md for private security reporting.
- Before public stable release, create and securely back up a production signing key; current alpha APKs use a debug certificate. Plan upgrade migration explicitly before changing keys.
- Telegram announcement channel with a linked moderated support group. Pin genuine download/source links and support-wallet network. Channel/repository names are proposals until created; no channel or repository was created by this change.
- A small documentation/download site with privacy statement, quickstart, protocol guide and known issues. Optional package-store distribution comes after stability/signing checks, not before.
- Never publish private server credentials or user diagnostic logs. A public shared WireGuard client key is not suitable for many concurrent devices; each device needs a distinct peer identity.
